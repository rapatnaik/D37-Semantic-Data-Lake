# Discovery & Metadata Assembly

This documents the discovery and metadata components of the D37 Analysis Agent. These modules identify files in unfamiliar directories and organize the results from the team's analyses into structured metadata.

The main files are:
- `discovery.py` — File identification and inventory creation
- `metadata.py` — Metadata assembly from analysis results
- `contracts.py` — Shared data structures and validation

## 1. Discovery (`discovery.py`)

### Function

`discover(root) -> Inventory`

Discovery scans a given directory and creates an inventory of the files available for analysis. It recursively identifies files and assigns each one a `SourceRef` containing its relative path, format, size, modification time, and stable ID.

It also creates a `ComponentRef` for each logical unit of data, such as a table, image, or document. Currently, discovery generally creates one component per file.

### Supported Formats

| Type | Formats |
|---|---|
| Tables | CSV, TSV, JSON, JSONL, Parquet, XLSX |
| Images | PNG, JPEG, TIFF |
| Documents | TXT, Markdown, PDF, DOCX |

Format identification uses file signatures, extensions, and limited file inspection. For Excel and Word documents, the module checks internal ZIP filenames to distinguish the two formats without extracting their contents.

### Safety and Limitations

Discovery is read-only and includes several checks:

- Excludes hidden entries, common credential files, caches, and generated output directories
- Skips symbolic links and checks that discovered files remain within the selected directory
- Does not execute code found during discovery
- Keeps unsupported files in the inventory as `unknown`, with their limitations recorded

Discovery only identifies candidate formats; it does not validate or analyze the actual data. For example, it can identify an Excel workbook but does not read its worksheets. It also does not automatically group files belonging to the same sample.

The current filename-based exclusions cannot detect every sensitive file, and ZIP inspection does not yet have explicit resource limits.

## 2. Metadata Assembly (`metadata.py`)

### Function

`build_metadata(component_id, results) -> dict`

The metadata builder takes a component ID and a collection of `ToolResult` objects generated by the EDA tools.

Previously, my metadata agent directly read datasets and calculated statistics using pandas and DuckDB. With the new architecture, the individual analysis tools handle those calculations, while `metadata.py` assembles their results without repeating the work.

### Validation and Assembly

The function checks that:

- The component ID is valid and at least one result is provided
- Every input is a valid `ToolResult`
- All results belong to the specified component
- No two results have the same `result_id`

It then collects the source IDs and preserves each result's measurements, methods, parameters, coverage, limitations, and artifact references.

Keeping results separate is important because different tools may analyze different parts of the same component. For example, one result might describe the entire dataset, while another might be based on a sample.

### Output

The output is a JSON-compatible dictionary with the following structure:

```json
{
  "schema_version": "1.0",
  "component_id": "c_patients",
  "result_count": 1,
  "source_ids": ["s_patients"],
  "results": [
    {
      "result_id": "r_counts",
      "component_id": "c_patients",
      "status": "complete",
      "inputs": ["s_patients"],
      "method": "example_csv_counts",
      "parameters": {},
      "coverage": {
        "mode": "full",
        "unit": "rows",
        "examined": 10,
        "total": 10,
        "selection": "all rows",
        "seed": null
      },
      "measurements": {
        "row_count": 10
      },
      "artifacts": [],
      "limitations": [],
      "schema_version": "1.0"
    }
  ]
}
```

This is a simplified example. The actual measurements depend on what the upstream analysis tool returns.

### Limitations and Integration

The metadata builder does not reopen datasets or independently verify the statistics it receives. It validates the `ToolResult` structure and checks component consistency, but source references should also be checked against the discovery inventory using `validate_references(inventory)`.

The new metadata JSON format also differs from the original CSV metadata agent's output. The existing CSV pipeline is being preserved separately while we confirm the measurement structure of Manasa's table profiler.

## 3. Testing

Tests are located under `tests/investigator/`.

| Test file | Coverage |
|---|---|
| `test_discovery.py` | Format recognition, mixed directories, file exclusions, stable IDs, unsupported inputs |
| `test_contracts.py` | Data validation, source references, JSON serialization, coverage |
| `test_metadata.py` | Metadata assembly, duplicate IDs, sampling, partial results, artifact preservation, JSON serialization |

Run the individual tests from the repository root:

```sh
python3 -m unittest discover -s tests/investigator -p 'test_discovery.py' -v
python3 -m unittest discover -s tests/investigator -p 'test_contracts.py' -v
python3 -m unittest discover -s tests/investigator -p 'test_metadata.py' -v
```

These tests use synthetic data and mock analysis results, allowing discovery and metadata assembly to be tested independently of the full pipeline.

## 4. Remaining Integration

The discovery and metadata modules have been implemented and tested individually. The remaining work is to verify metadata assembly using the production EDA outputs, confirm consistent measurement fields across tools, and complete end-to-end testing with the rest of the investigation pipeline.
